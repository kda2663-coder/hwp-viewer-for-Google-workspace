# 설계 결정 기록 (Decision Log)

이 문서는 **"왜 이렇게 만들었나 / 어떤 길을 피했나"** 를 남긴다.
코드만 보면 *결과*는 알지만 *왜 그 길로 갔는지, 어떤 막다른 길에서 돌아왔는지*는 안 보인다.
같은 고민·같은 실수를 반복하지 않으려고 적는다.

각 항목은 **상황 → 고려한 선택지 → 결정 → 이유 → 피한 함정** 순서.

---

## 1. 편집기 → 뷰어로 전환

- **상황**: 처음엔 rhwp 엔진으로 브라우저에서 hwp를 *편집*하고 드라이브 원본에 다시 저장하는 걸 만들었다(성공까지 함).
- **고려**: (a) 편집+저장 유지 (b) 읽기 전용 뷰어로 축소
- **결정**: (b) 뷰어.
- **이유**: rhwp가 저장할 때 파일을 **다시 만들어내는데(re-serialize)**, 한글의 복잡한 서식이 그 과정에서 **깨질 수 있다**. 드라이브 버전관리로 복구는 되지만 "원본을 망가뜨릴 수 있다"는 근본 위험이 남는다. 뷰어는 그 위험이 0.
- **피한 함정**: "되니까 좋다"가 아니라 "원본 손상 가능성"을 기준으로 판단. 편집 기능 코드는 지우지 않고 남겨둠(복구용, 호출 안 됨).

---

## 2. 진짜 한글로 편집 = 로컬 도우미 (rhwp 편집이 아니라)

- **상황**: 뷰어로 바꿨지만 "편집하고 싶다"는 욕구는 남음.
- **고려**: (a) rhwp 편집 되살리기 (b) PC에 설치된 진짜 한글 프로그램으로 원본 열기
- **결정**: (b) 로컬 도우미(Node 서버)가 PC 한글 프로그램 실행.
- **이유**: 진짜 한글이 열면 **원본 손상 위험이 애초에 없다**(1번 문제 회피). rhwp 편집의 약점을 우회.
- **피한 함정**: "브라우저에서 다 끝내기"에 집착하지 않음. 브라우저는 보안상 PC 프로그램을 직접 못 켜므로, 로컬 도우미라는 별도 부품이 불가피함을 수용. 대신 부가기능(node 깐 소수)으로 위치 조정.

---

## 3. 확장 ID 의존 제거 — 로그인을 확장 → 웹앱으로 이동

- **상황**: 확장이 직접 구글 로그인/다운로드를 했는데, 그 OAuth가 **확장 ID에 묶여서** 다른 PC(다른 ID)에서 깨짐.
- **고려**: (a) 확장이 계속 로그인 (b) 로그인·다운로드를 웹앱으로 옮기고 확장은 "감지+링크"만
- **결정**: (b).
- **이유**: 웹앱 로그인은 확장 ID와 무관 → 누구 PC에서도 작동. 같은 일(드라이브 파일 받기)을 확장·웹앱 **두 곳에 중복 구현**하던 것도 한 곳(웹앱)으로 정리됨.
- **피한 함정**: 중복 구현은 "한 곳이 깨지면 원인 추적이 어렵다". 핵심 엔진은 웹앱 하나, 확장은 얇은 진입점 — 이 역할 분리가 정석.

---

## 4. OAuth scope: readonly ↔ drive.file (왔다갔다 → drive.file 확정)

- **상황**: 확장이 넘긴 fileId를 웹앱이 직접 읽으려고 한때 `drive.readonly`로 **올렸다**. 그러다 마켓 심사 단계에서 다시 검토.
- **핵심 사실**:
  - `drive.readonly` = **"제한된 범위(restricted)"** = 드라이브 전체 읽기. 강력 → 구글이 **CASA 보안평가(유료·제3자·매년 갱신) + 매년 재인증**을 요구하는 정규 경로.
  - `drive.file` = **"민감하지 않은 범위"** = 앱으로 연 파일만. → **OAuth 인증 자체가 불필요**(콘솔 인증센터가 "인증 필요 없음" 표시로 확인됨). 보안평가·재인증 없음.
- **헷갈렸던 점**: "readonly가 이름상 약해 보인다"(읽기 전용이니까). 실제로 **동작은 약하지만 범위가 넓어서** 더 위험 등급. 구글이 보는 기준은 *동작*이 아니라 ***범위***다. "전부 훔쳐보기" > "한 장 고쳐쓰기".
- **결정**: `drive.file` 확정.
- **이유**: 우리는 뷰어 + (선택적) 로컬편집이라 "앱으로 연 파일만"으로 충분. 무료·명성 목적 오픈소스에 "매년 보안평가 갱신"은 과한 평생 부담.
- **피한 함정**: 한 번 readonly로 올렸다 drive.file로 내리면 **재인증**이라 되돌리기 비쌈 → 처음부터 가장 좁은 범위로 가는 게 정석("가능한 가장 좁은 OAuth 범위" = 구글 권고이자 통과 지름길).

## 5. 한글편집 경로 찾기: 드라이브 API → PC 로컬 DB

- **상황**: 4번에서 drive.file로 정하니, 기존 "한글로 편집"이 깨짐. 그 기능은 파일의 **전체 경로**(`내드라이브\폴더\...\파일.hwp`)가 필요한데, 경로를 만들려면 부모 폴더 이름들을 읽어야 함. **drive.file은 부모 폴더 접근이 403으로 막힘**(앱으로 연 파일만 보이니까). Picker를 써도 부모폴더 *이름*은 못 읽음(ID만 줌).
- **고려**: (a) 편집 포기 (b) readonly 유지(보안평가 감수) (c) **PC의 Drive 메타DB에서 경로 찾기**
- **결정**: (c).
- **이유 / 원리**: Google Drive 데스크톱 앱이 PC에 깔아두는 메타DB(`%LOCALAPPDATA%\Google\DriveFS\<계정ID>\metadata_sqlite_db`)는 **평문 SQLite**이고 모든 파일·폴더의 ID↔이름↔부모 관계를 담고 있다. 도우미(PC 프로그램)가 **구글 API 대신 이 로컬 DB에서** fileId로 경로를 조립하면 **권한이 아예 필요 없다**. → drive.file로도 편집 가능.
- **검증(2026-05-31)**: Node `node:sqlite`(v22.13+ 내장)로 readonly+immutable 열기, fileId→경로 조립 **2ms**. 내 드라이브·공유 드라이브 둘 다 OK. items 테이블에 `local_title` 컬럼이 직접 있어 protobuf 파싱 불필요. `stable_parents` 테이블로 부모 추적.
- **피한 함정**:
  - "Picker로 부모폴더 받으면 되겠지" → ID만 주고 이름은 drive.file로 못 읽음. 추측 말고 실제 확인하니 막혀 있었음.
  - 비공식 방식이라 구글이 DB 구조를 바꾸면 깨질 수 있음(트레이드오프 수용). 대신 권한·심사 부담이 0.

---

## 6. 마켓플레이스(연결앱) vs 크롬 확장 — 진입 통로 2개

- **상황**: 같은 "드라이브 hwp → 뷰어"를 여는 통로가 둘.
- **결정**: **마켓플레이스가 본체**, 확장은 곁가지.
- **이유**: 마켓은 **모바일도 됨**(드라이브앱→연결앱→브라우저), 확장은 모바일 불가. 마켓이 상위호환에 가까움. 둘 다 진입 후엔 "뷰어 → (옵션) 한글로 편집" 흐름으로 동일.
- **피한 함정**: 처음 구상("확장이 한글 설치 여부를 감지해 미리 로컬열기/뷰어를 갈라줌")은 불가 — 브라우저는 PC 프로그램 설치 여부를 모름. 그래서 **"항상 뷰어로 열고, 편집은 버튼 클릭 시 도우미 켜짐 여부로 분기"** 가 더 단순·견고하고 모바일까지 커버.

---

## 7. 마켓 등록 체크박스 — "확인 안 된 건 선언하지 않는다"

- **여러 파일 지원**: ❌ — 코드가 한 번에 1개만 연다. 선언과 실제가 다르면 거절 사유.
- **공유 드라이브 지원**: ✅ — 코드에 `supportsAllDrives=true` 있고 실제 작동 확인됨.
- **가져오기(Import)**: ❌ — 구글 문서 변환 기능. hwp와 무관.
- **모바일 브라우저**: 처음엔 ❌(미검증이라). 원칙은 **"심사관이 실제로 테스트 가능한 항목을, 우리가 확인 안 한 채 '된다'고 선언하면 거절"**. 검증 후 켜는 게 안전.
- **피한 함정**: "목표니까 체크"가 아니라 "지금 검증됐나"로 판단. 미검증 선언은 거절 1순위.

---

## 8. 출시 전략 — 뷰어 먼저, 편집은 통과 후 스위치

- **결정**: 한글편집 버튼을 `EDIT_ENABLED` 플래그 뒤에 숨겨 심사 제출. 통과 후 `true`로 켬.
- **이유**: 편집 기능이 심사에서 오해(예: "저장 코드 있는데 왜 readonly냐") 살 여지를 차단. **켜는 작업이 scope를 안 건드리므로** 통과 후 켜도 재심사 불필요.
- **피한 함정**: 심사 중 "수정 못 한다"는 **마켓 등록정보(이름·scope·스샷)** 얘기지, **웹앱 코드 배포는 무관**. scope만 안 건드리면 코드는 언제든 배포 가능.

---

## 한 줄 교훈 모음
- 권한은 **동작이 아니라 범위**로 위험도가 정해진다. 가장 좁은 범위가 통과 지름길.
- "될 것 같다"는 **실제로 확인**한다(Picker 부모폴더, DriveFS DB 둘 다 추측이 아니라 테스트로 결론냄).
- 미검증 기능은 **선언하지 않는다**(마켓 체크박스).
- 위험한 자동화(원본 자동저장)보다 **안전한 수동·복사본**이 나을 때가 있다.
- 되돌리기 비싼 결정(scope 승격→재인증)은 **처음에 신중히**.
